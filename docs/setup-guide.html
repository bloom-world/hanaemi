01

事前準備

プロダクトオーナー所要 半日

各サービスのアカウントを「個人のもの」で作ると、担当者が退職したときに会社が管理できなくなります。最初に会社として持つ共通のものを用意します。

  1. 会社の登記情報を英語表記で揃える

    Apple・Google・D-U-N-S では、登記上の正式な会社名（英語表記）、所在地（英語表記）、代表電話番号を入力します。全サービスで同じ表記に統一してください。表記がずれると審査で差し戻されます。

  2. 共通のメールアドレスを作る

    例: dev-admin@会社ドメイン。各サービスのオーナーアカウントはこのアドレスで作ります。複数人が受信できるグループアドレス（Google グループなど）にしておくと、担当者の不在時も対応できます。

    Google Play 用に、このアドレスで Google アカウントも必要です（会社が Google Workspace ならそのまま使えます）。

  3. パスワード管理ツールを用意する

    1Password や Bitwarden の「チーム（ビジネス）」プランで共有の保管庫（Vault）を作ります。ここにパスワード、二段階認証の復旧コード、後で出てくる鍵ファイル（Apple の .p8、Android の keystore、Google のサービスアカウント JSON）を保管します。

    鍵やパスワードをチャットやメールで送らないでください。必ずパスワード管理ツール経由で共有します。

  4. 二段階認証用の端末を決める

    Apple のアカウントは、確認コードを受け取る iPhone か電話番号が必要です。会社の共用 iPhone か、管理責任者の端末を登録します。認証アプリ（Google Authenticator など）を使う場合は、復旧コードを必ずパスワード管理ツールに保存してください。

  5. 支払い用の法人カードを用意する

    Apple、Google、Firebase（Blaze の場合）、Codemagic はクレジットカード払いです。海外サービスの決済ができる法人カードを用意します。

  6. 会社の Web サイトがあるか確認する

    Apple の法人登録では、会社ドメインの Web サイトと、そのドメインのメールアドレスが求められます。サイトが無い場合は簡単なものでも先に用意してください。

  7. アプリの識別子（Bundle ID）を決める

    アプリを一意に表す ID で、公開後は変更できません。会社ドメインを逆にした形が一般的です（例: 会社ドメインが example.co.jp なら jp.co.example.hanaemi）。エンジニアと相談して決めます。iOS と Android で同じものを使います。

02

D-U-N-S 番号の確認・取得

プロダクトオーナー作業 30分 ＋ 発行待ち 最大2週間程度無料

D-U-N-S（ダンズ）番号は、会社ごとに割り振られる 9 桁の番号です。Apple と Google Play に「法人」として登録するときに必須です。日本では東京商工リサーチ（TSR）が管理しています。すでに番号を持っている会社も多いので、まず確認します。

  1. Apple の検索ツールで番号の有無を確認する

    Apple Developer サイトの D-U-N-S 番号の案内ページ（developer.apple.com/support/D-U-N-S）から検索ツールを開きます。検索には Apple アカウントでのサインインが必要です（次章の手順 1 で作るアカウントを先に作っておくとスムーズです）。

    会社名（英語）、所在地、電話番号を入力して検索します。すでに番号がある場合は、検索結果としてその場で画面に表示されます（メールを待つ必要はありません）。

  2. 見つかった場合: 登録内容を確認する

    表示された会社名・住所が正しいか確認し、番号と英語表記の会社名をそのまま控えます。Apple の登録ではこの表記と完全に一致させる必要があります。住所などが古い場合は TSR に変更を依頼します。

  3. 見つからない場合: 同じツールから新規申請する

    検索結果が無いときは、そのまま申請フォームに進めます。会社情報と連絡先を入力して送信します。申請後、TSR から確認の連絡（メール・電話）が来ることがあるので対応してください。

    番号が発行されると、申請時に入力したメールアドレスに番号が届きます。発行まで最大 2 週間程度かかります。発行後、Apple のシステムに反映されるまでさらに数日かかることがあります。

  4. 番号をパスワード管理ツールの共有メモに記録する

    番号、登録された英語の会社名・住所を記録し、Google Play の登録でも同じ情報を使います。

03

GitHub（ソースコード管理）

プロダクトオーナー所要 30分無料〜

ソースコードは、プロダクトオーナーの個人の GitHub アカウントにリポジトリ（コードの置き場所）を作り、そこにエンジニアを「コラボレーター」として招待して運用します。以下、このアカウントを「リポジトリのオーナー」と呼びます。Codemagic と Web の自動公開（GitHub Actions）も、このオーナーのアカウントを通して設定します。

  1. GitHub アカウントを用意する

    プロダクトオーナー

    アカウントがなければ github.com/signup で作成します。既存のアカウントを使っても構いません。

    右上のアイコン → Settings → Password and authentication

    二段階認証を有効にします。復旧コードはパスワード管理ツールに保存します。

  2. リポジトリの構成をエンジニアと決める

    プロダクトオーナー エンジニア

    アプリ（Flutter）、Web（React）、Firebase の設定（Cloud Functions のコード、セキュリティルールなど）を 1 つのリポジトリにまとめるか、分けるかをエンジニアに決めてもらいます。リポジトリ名もここで決めます（例: hanaemi）。

  3. リポジトリを作る

    プロダクトオーナー

    右上の「＋」→ New repository

    • Owner: 自分のアカウント
    • Repository name: 手順 2 で決めた名前
    • 公開範囲: Private（非公開）を必ず選ぶ
    • README などの初期ファイル: エンジニアの指示に従う（迷ったら何も追加しない）

    リポジトリを分ける場合は、その数だけ作ります。

  4. エンジニアを招待する

    プロダクトオーナー

    リポジトリの画面 → Settings → Collaborators → Add people

    エンジニアの GitHub ユーザー名かメールアドレスを入力して招待します。エンジニアに招待メールのリンクから承認してもらうと完了です（招待の有効期限は 7 日。切れたら招待し直します）。リポジトリが複数ある場合は、それぞれで招待します。

  5. オーナーにしかできない操作を把握しておく

    プロダクトオーナー

    個人アカウントのリポジトリでは、招待されたエンジニアはコードの追加・変更はできますが、次の操作はオーナーにしかできません。エンジニアから依頼があったら対応します。

    • メンバーの追加・削除
    • Codemagic などの外部サービスとの連携の許可（9 章）
    • GitHub Actions の秘密の値の登録（Web の自動公開、8 章）
    • リポジトリの設定変更（ブランチの保護ルールなど）
    • リポジトリの名前変更・移管・削除

    非公開リポジトリで「ブランチの保護ルール」（レビューなしでの反映を防ぐ設定）を使うには、オーナーのアカウントが有料の GitHub Pro（月 4 USD 程度）である必要があります。必要かどうかはエンジニアと相談してください。

将来、体制が変わったとき

オーナーの交代や、会社の Organization での管理に切り替えたくなった場合は、リポジトリを移管（Settings → Danger Zone → Transfer ownership）できます。移管後も古い URL は新しい URL に転送されます。ただし、Codemagic の連携と GitHub Actions の秘密の値は、移管先で設定し直しが必要です。

04

Apple Developer Program（iOS）

プロダクトオーナー作業 1時間 ＋ 審査 数日〜2週間年 99 USD

iOS アプリを実機で動かす、TestFlight でテスト配信する、App Store に公開する、のすべてに必要です。法人（Organization）として登録します。個人で登録すると、ストアに個人名が表示され、後から法人に移すのに手間がかかります。

申請する人について: 申請者は、会社を代表して Apple の契約に同意する権限がある人（代表者、または代表者から権限を与えられた人）である必要があります。審査中に Apple から申請者本人宛てに確認の電話が来ることがあります。

A. 登録（法人）

  1. Apple アカウントを作る

    account.apple.com で共通メールアドレス（会社ドメインのもの）を使って作成します。二段階認証が必須です。氏名は申請者本人の実名にします。

  2. D-U-N-S 番号が Apple に反映されているか確認する

    前章で確認した番号を使います。新規取得した場合は、Apple 側に反映されるまで待ってから次に進みます。

  3. 登録を開始する

    developer.apple.com/programs/enroll から「登録を開始」を選びます。iPhone / Mac の「Apple Developer」アプリからも登録できます。

  4. 「組織（Organization）」を選んで会社情報を入力する

    • 法人名: D-U-N-S に登録されている英語表記と完全に同じにする
    • D-U-N-S 番号
    • 会社の Web サイト（会社ドメインのもの）
    • 勤務先メールアドレス（会社ドメインのもの）、電話番号
    • 申請者の役職、法的な権限の有無

  5. Apple の確認を待つ

    Apple が会社情報と申請者の権限を確認します。数日〜2 週間程度かかります。電話やメールで追加の確認が来たら対応します。

  6. 年会費を支払う

    承認のメールが届いたら、案内に従って法人カードで支払います。支払い後に「メンバーシップ有効化」のメールが届けば登録完了です。自動更新を有効にしておくと、期限切れでアプリが配信停止になるのを防げます。

B. 契約・税金・口座（課金をするなら必須）

  1. App Store Connect にサインインする

    appstoreconnect.apple.com に同じ Apple アカウントでサインインします。

  2. 無料アプリの契約に同意する

    ビジネス（Business）→ 契約

    最新の利用規約への同意を求められたら同意します。規約の更新に同意していないと、テスト配信や審査提出ができなくなることがあります。Account Holder（登録した本人）にしか同意できないので、定期的に確認してください。

  3. 有料アプリの契約を結ぶ（アプリ内課金をする場合）

    「有料 App」の契約で、次を登録します。

    • 銀行口座（売上の入金先）
    • 税務情報: 日本の法人は米国の税務フォーム W-8BEN-E を画面上で入力します。日米租税条約の適用欄があるので、分からなければ税理士に確認してください
    • 連絡先（経理・法務・技術など）

    課金をしない場合でも、後から追加できます。審査に数日かかるので、課金する予定なら早めに済ませます。

C. メンバーの招待

  1. エンジニアを App Store Connect に招待する

    App Store Connect → ユーザとアクセス → 「＋」

    氏名とメールアドレス（本人の Apple アカウント）を入力し、役割を選びます。

    役割できること付ける相手
    Admin（管理）ほぼすべて。ユーザーの招待、API キーの発行管理責任者、リーダーエンジニア
    App Manager（App マネージャ）アプリの情報編集、TestFlight、審査提出リーダーエンジニア、PM
    Developer（デベロッパ）ビルドのアップロード、TestFlight の確認エンジニア
    Marketing（マーケティング）ストア掲載情報の編集マーケティング担当

    エンジニアには「証明書、ID、プロファイルへのアクセス」（デベロッパリソース）にもチェックを入れます。これがないと開発用の証明書を作れません。

  2. テスト配信だけ見る人も招待する

    社内の確認者は、役割を「Customer Support」などの権限の小さいものにして招待し、TestFlight の内部テスターに追加します（10 章）。社外の人は招待せず、TestFlight の外部テスターにします。

D. 自動配信用の鍵を発行する（Codemagic 用）

  1. App Store Connect API のアクセスを申請する（初回のみ）

    ユーザとアクセス → 統合（Integrations）→ App Store Connect API

    初めて使うときは Account Holder が「アクセスをリクエスト」して利用規約に同意します。

  2. チームキーを作成する

    「チームキー」で「＋」を押し、名前（例: Codemagic）とアクセス権「App Manager」を選んで作成します。

  3. 3 つの情報を保管する

    • Issuer ID（画面上部に表示）
    • キー ID（作成したキーの行に表示）
    • .p8 ファイル（「API キーをダウンロード」）。ダウンロードは 1 回しかできません。すぐにパスワード管理ツールに保存してください

    この 3 つを 9 章で Codemagic に登録します。

  4. プッシュ通知用の鍵（APNs キー）を作る

    エンジニア

    developer.apple.com → Certificates, Identifiers & Profiles → Keys → 「＋」

    「Apple Push Notifications service (APNs)」にチェックを入れて作成し、.p8 ファイルをダウンロードします（こちらも 1 回のみ）。キー ID とチーム ID も控えます。6 章で Firebase に登録します。権限によってはエンジニアが作業できないので、その場合は Admin が作成します。

05

Google Play Console（Android）

プロダクトオーナー作業 1時間 ＋ 確認 数日〜初回のみ 25 USD

Android アプリのテスト配信と Google Play への公開に必要です。こちらも「組織」アカウントで作ります。

なぜ組織アカウントか: 個人アカウントで新規登録した場合、本番公開の前に「12 人以上のテスターで 14 日間のクローズドテスト」が義務付けられています。組織アカウントにはこの条件がありません（条件は変わることがあるので、登録時に確認してください）。

A. 登録（組織）

  1. 会社の Google アカウントでサインインする

    共通メールアドレスの Google アカウントを使います。二段階認証を有効にします。

  2. Play Console に登録を開始する

    play.google.com/console/signup を開き、アカウントの種類で「組織」を選びます。

  3. お支払いプロファイル（組織）を作る

    組織名、所在地、D-U-N-S 番号を入力します。D-U-N-S の情報と一致させてください。

  4. デベロッパー情報を入力する

    • デベロッパー名: Google Play のアプリページに表示される名前（例: 会社名）
    • 組織の Web サイト、組織の電話番号
    • 連絡先メールアドレス・電話番号（Google から確認コードが送られます）
    • アプリの予定（何本くらい、どんな種類かなど）を答える質問

  5. 登録料を支払う

    25 USD を法人カードで支払います。

  6. 本人確認・組織の確認を済ませる

    申請者の本人確認（身分証の提出）や、組織の書類（登記事項証明書など）の提出を求められることがあります。Play Console のホーム画面に表示される案内に従います。確認が終わるまで数日かかります。

B. メンバーの招待

  1. エンジニアを招待する

    Play Console → ユーザーと権限 → 新しいユーザーを招待

    エンジニアの Google アカウントのメールアドレスを入力し、権限を選びます。

    • リーダーエンジニア: 「管理者（すべての権限）」
    • エンジニア: アプリ単位で「テストトラックへのリリース」「アプリ情報の閲覧」など
    • 本番公開の権限（製品版トラックへのリリース）は限られた人だけに付けます

C. アプリの作成と申告（エンジニアと一緒に）

  1. アプリを作成する

    Play Console → すべてのアプリ → アプリを作成

    アプリ名（後で変更可）、デフォルトの言語（日本語）、「アプリ」、「無料」を選びます。一度「無料」で公開すると有料アプリには変更できません。アプリ内課金は無料アプリでも可能です。

  2. 「アプリのコンテンツ」の申告を埋める

    Play Console → アプリ → ポリシー → アプリのコンテンツ

    • プライバシーポリシーの URL（8 章の Web で公開）

    プロジェクト名用途
    hanaemi-dev開発

    月の予算額（例: 5,000 円）と、通知するタイミング（予算の 50%・90%・100% など）、通知先のメールアドレスを設定します。予算を超えても自動では止まらないので、通知を受けたら誰が確認するかも決めておきます。

  4. エンジニアを招待する

    プロダクトオーナー

    プロジェクト → 歯車アイコン → ユーザーと権限 → メンバーを追加

    エンジニアの Google アカウントのメールアドレスと役割を入力します。プロジェクトごとに招待が必要です。

    役割できること付ける相手
    オーナーすべて（メンバー管理、支払い設定を含む）プロダクトオーナー、リーダーエンジニア

    閲覧者見るだけ確認者

  5. データの保存場所（ロケーション）を決める

    プロダクトオーナー エンジニア

B. エンジニアの作業

  1. アプリと Web を登録する

    エンジニア

    各プロジェクトに iOS・Android・Web のアプリを登録し、設定ファイルをアプリに組み込みます（FlutterFire CLI を使うと環境ごとにまとめて設定できます）。

  2. ログイン方法を有効にする

    エンジニア

    Authentication → Sign-in method

    • メール / パスワード
    • Google（下の手順 C の同意画面の設定が必要）
    • Apple（Apple Developer で「Sign in with Apple」用の設定と鍵が必要。Apple 側の作業に Admin 権限が要る場合はプロダクトオーナーが対応）

    Authentication → 設定 → 承認済みドメイン に、Web（8 章）の独自ドメインを追加します。

  3. データベースとファイル保存のルールを書く

    エンジニア

    Firestore と Cloud Storage の「セキュリティルール」で、「本人のデータは本人だけが読み書きできる」などの制限をかけます。初期設定のテストモードのまま公開しないことが重要です。ルールはファイルで管理し、stg → prod の順に反映します。

  4. APNs キーを登録する

    エンジニア

    プロジェクトの設定 → Cloud Messaging → Apple アプリの構成

    4 章 D で作った APNs キー（.p8）、キー ID、チーム ID を登録します。これで iOS にもプッシュ通知が届きます。

  5. 不正なアクセスを防ぐ（App Check）

    エンジニア

    エンジニア

    prod が Blaze なら、Firestore の定期バックアップ（または PITR）を設定します。Spark の場合はバックアップの手段がないため、プロダクトオーナーと方針を相談します。

07

ドメイン・認証メール

プロダクトオーナーエンジニア所要 1時間 ＋ DNS 反映待ち

会員登録の確認メールやパスワード再設定メールは、Firebase Authentication が送ります。初期設定では送信元が noreply@プロジェクトID.firebaseapp.com になるため、自社ドメインから送るように設定します（迷惑メールに入りにくくなり、ユーザーにも分かりやすくなります）。

  1. 使うドメインを決める

    プロダクトオーナー

    既存の会社ドメインを使うか、サービス用のドメイン（例: hanaemi.jp）を取得するか決めます。新しく取る場合は、お名前.com や Cloudflare Registrar などのドメイン取得サービスで取得します。ドメインの管理画面（DNS の設定）に入れる人を確認しておきます。

    決めておくアドレスの例: Web（hanaemi.jp）、管理画面（admin.hanaemi.jp）、メールの送信元（noreply@hanaemi.jp）、問い合わせ先（support@…）。

  2. Firebase でメールの送信元ドメインを設定する

    プロダクトオーナー エンジニア

    Firebase（prod）→ Authentication → テンプレート → いずれかのテンプレートの編集（鉛筆アイコン）→ ドメインをカスタマイズ

    送信に使うドメインを入力すると、DNS に追加するレコード（TXT / CNAME）が表示されます。

  3. DNS にレコードを追加する

    プロダクトオーナー

    ドメインの管理画面（DNS の設定）を開き、表示されたレコードをそのままコピーして追加します。反映に数時間〜最大 48 時間ほどかかります。Firebase の画面で確認が完了すると、送信元を自社ドメインのアドレスに変更できます。迷惑メール扱いを減らすため、DMARC レコードも追加しておくとよいです。

  4. メールの文面を日本語にする

    プロダクトオーナー エンジニア

    Authentication → テンプレート → テンプレートの言語

    言語を日本語にし、送信者名（例: hanaemi）、件名、本文を確認します。文面はプロダクトオーナーが用意し、エンジニアが設定します。stg / prod それぞれのプロジェクトで設定が必要です。

  5. メールのリンクからアプリに戻す設定

    エンジニア

    確認メール・再設定メールのリンクを押したときに、アプリや Web に戻るための設定（アクション URL、ディープリンク）を行います。

送れる数について: Firebase Authentication からのメール送信には 1 日あたりの上限があります。上限に近づく規模になった場合や、お知らせメールなど認証以外のメールを送る場合は、メール送信サービス（Resend、SendGrid など）の追加をエンジニアと検討します。

08

Web（React）の公開: Firebase Hosting

プロダクトオーナーエンジニア所要 1時間 ＋ DNS 反映待ち無料枠あり

React で作る Web（運営用の管理画面、利用規約・プライバシーポリシーのページなど）は、6 章で作った Firebase のプロジェクトで公開します。アカウントや支払いを増やさずに済み、ログインやデータベースとも同じプロジェクトで管理できます。

Firebase での公開方法について: Firebase には「Hosting」と「App Hosting」があります。React の画面だけを配信するなら Hosting、サーバー側で画面を作る構成（Next.js など）なら App Hosting を使います（App Hosting は Blaze プランが必要）。どちらにするかはエンジニアが決めます。以下は Hosting の場合の流れです。

A. 公開先の準備

  1. 公開するサイトの分け方を決める

    プロダクトオーナー エンジニア

    1 つの Firebase プロジェクトに複数のサイトを作れます。例えば次のように分けます。

    サイトアドレスの例見られる人
    公開ページ（利用規約・プライバシーポリシー・アカウント削除の案内・LP）hanaemi.jp誰でも
    管理画面admin.hanaemi.jp運営メンバーのみ（ログイン必須）

  2. Hosting を有効にする

    エンジニア

    Firebase（stg / prod）→ 構築（Build）→ Hosting → 始める

    サイトを追加し、エンジニアが Firebase CLI で公開の設定をします。公開すると、まず プロジェクトID.web.app のアドレスで見られるようになります。

  3. GitHub と連携して自動公開にする

    プロダクトオーナー エンジニア

    エンジニアが設定すると、コードの更新時に GitHub Actions が自動で公開し、プルリクエストごとに確認用のプレビュー URL も作られます（stg の確認に使えます）。

    設定の途中で、GitHub のリポジトリに「秘密の値（Firebase に公開するための鍵）」を登録する操作があります。これはリポジトリのオーナー（プロダクトオーナー）にしかできないので、エンジニアと画面を共有しながら一緒に作業するか、オーナーが登録します。

B. ドメイン

  1. 独自ドメインを追加する

    プロダクトオーナー エンジニア

    Firebase（prod）→ Hosting → カスタムドメインを追加

    公開に使うアドレス（例: hanaemi.jp、admin.hanaemi.jp）を入力すると、DNS に追加するレコード（TXT・A など）が表示されます。

  2. DNS にレコードを追加する

    プロダクトオーナー

    ドメインの管理画面を開き、表示されたレコードをそのまま追加します。確認とセキュリティ証明書（https）の発行が自動で行われ、数時間〜最大 24 時間ほどで独自ドメインで見られるようになります。

    会社ドメインですでに Web サイトやメールを使っている場合、既存のレコードを消したり書き換えたりしないよう注意してください。不安な場合はエンジニアと一緒に作業します。

  3. ログインを許可するドメインに追加する

    エンジニア

    Authentication → 設定 → 承認済みドメイン

    管理画面の独自ドメインを追加します。追加しないと、管理画面でログインできません。

C. 管理画面と公開ページ

  1. 管理画面に入れる人を限定する

    エンジニア

    管理画面は Firebase Authentication でのログインを必須にし、さらに「運営メンバー」の権限（カスタムクレーム）を持つアカウントだけが操作できるようにします。データベースのルール側でも、運営メンバー以外は管理用のデータを読み書きできないようにします。画面を隠すだけでなく、データ側で必ず制限することが重要です。

    運営メンバーの追加・削除の手順（誰が、どうやって権限を付けるか）をエンジニアに用意してもらいます。

  2. プライバシーポリシーと利用規約のページを公開する

    プロダクトオーナー

    ストアの審査と Google ログインの設定で URL が必要です。文面は法務・専門家に確認のうえ用意し、エンジニアにページ化を依頼します。アカウント削除の方法を説明するページも必要です（Google Play の申告で求められます）。これらのページは誰でも見られる公開ページ側に置きます。

09

Codemagic（自動ビルド・テスト配信）

プロダクトオーナーエンジニア所要 1〜2時間従量課金など

GitHub にコードが入ると、Codemagic が自動でアプリをビルドし、TestFlight と Google Play の内部テストに配信します。iOS のビルドには Mac が必要ですが、Codemagic のクラウド上の Mac を使うので手元に Mac がなくても配信できます。

始める前に揃えておくもの: 3 章の GitHub リポジトリ、4 章 D の App Store Connect API キー（Issuer ID・キー ID・.p8）、5 章 D の Google サービスアカウントの JSON。Apple・Google の登録が終わる前でも、アカウント作成とチーム招待は先に進められます。

A. アカウントとチーム

  1. アカウントを作る

    プロダクトオーナー

    codemagic.io/signup から「GitHub でサインアップ」を選び、3 章のリポジトリのオーナーの GitHub アカウントで認証します。

  2. チームを作る

    プロダクトオーナー

    左メニュー → Teams → Create new team

    チーム名（例: 会社名）を入力します。チームで使うには支払い方法の登録が必要です。Billing で法人カードを登録し、料金プラン（ビルド時間に応じた従量課金、または固定料金）を選びます。最新の料金は codemagic.io/pricing で確認してください。

  3. メンバーを招待する

    プロダクトオーナー

    Teams → チーム名 → Team members → Invite

    エンジニアのメールアドレスを入力し、役割を選びます。リーダーエンジニアは Admin（設定や鍵の登録ができる）、他のエンジニアは Member。

  4. GitHub のリポジトリへのアクセスを許可する

    プロダクトオーナー

    アプリを追加する画面で GitHub と連携すると、GitHub 側で「Codemagic GitHub App」のインストール画面が開きます。インストール先にリポジトリのオーナーの個人アカウントを選び、「Only select repositories」で hanaemi のリポジトリだけを許可します。この操作はオーナーにしかできません。

B. 鍵の登録

  1. App Store Connect API キーを登録する

    プロダクトオーナー エンジニア

    Teams → チーム名 → Team integrations → Developer Portal → Connect

    キーの名前、Issuer ID、キー ID を入力し、.p8 ファイルをアップロードします。これで Codemagic が iOS の証明書の作成と TestFlight へのアップロードを自動で行えます。

  2. iOS の署名用証明書を用意する

    エンジニア

    Teams → チーム名 → Code signing identities → iOS certificates

    Codemagic 上で配布用の証明書を作成（または既存のものを取得）し、保存します。証明書の秘密鍵もパスワード管理ツールに保管します。

  3. Android の署名鍵（アップロード鍵）を作って登録する

    エンジニア

    Teams → チーム名 → Code signing identities → Android keystores

    エンジニアが keystore ファイルを作り、パスワード・エイリアスと一緒にアップロードします。Google Play では「Play アプリ署名」を使い、最終的な署名は Google が管理します。手元の keystore は「アップロード鍵」です。

    keystore ファイルとパスワードは必ずパスワード管理ツールにバックアップしてください。紛失すると、Google に再設定を依頼する手続きが必要になり、その間アップデートを出せません。

  4. Google Play の鍵（JSON）を登録する

    エンジニア

A. 共通: App Store Connect にアプリを登録する

TestFlight にアップロードする前に、アプリの「入れ物」を作ります。Codemagic を使う場合も必要です。

  1. Bundle ID を登録する

    エンジニア

    developer.apple.com → Certificates, Identifiers & Profiles → Identifiers → 「＋」→ App IDs

    1 章で決めた Bundle ID を登録し、使う機能（Push Notifications、Sign in with Apple など）にチェックを入れます。stg 用に別の ID（例: 末尾に .stg）を使う場合は、それも登録します。Xcode の自動署名で自動登録されることもあります。

  2. App Store Connect でアプリを作成する

    プロダクトオーナー エンジニア

    App Store Connect → アプリ →「＋」→ 新規 App

    • プラットフォーム: iOS
    • 名前: ストアに表示する名前（他のアプリと重複不可。後で変更可）
    • プライマリ言語: 日本語
    • バンドル ID: 手順 1 で登録したもの（後から変更不可）
    • SKU: 社内管理用の ID（例: hanaemi-ios。ユーザーには見えない）

    stg 版を別アプリとして TestFlight に出す場合は、stg 用の Bundle ID でもう 1 つ作ります（名前は「hanaemi STG」など）。

B. iOS: Mac から TestFlight へアップロードする

  1. Xcode に Apple アカウントを追加する（初回のみ）

    エンジニア

    Xcode → Settings → Accounts →「＋」→ Apple Account

    4 章 C で招待された自分の Apple アカウントでサインインし、チーム（会社名）が表示されることを確認します。

  2. 署名の設定をする（初回のみ）

    エンジニア

    Xcode で ios/Runner.xcworkspace を開く → Runner → Signing & Capabilities

    「Automatically manage signing」をオンにし、Team に会社のチームを選びます。フレーバー（dev / stg / prod）ごとに Bundle ID が正しいか確認します。必要な機能（Push Notifications など）を Capabilities に追加します。

  3. バージョンとビルド番号を上げる

    エンジニア

    pubspec.yaml の version: 1.0.0+12 の「+」の後ろ（ビルド番号）を、アップロードのたびに必ず増やします。同じビルド番号は 2 回アップロードできません。チームで番号が重ならないよう、誰が何番を使ったか記録します。

  4. アプリをビルドする

    エンジニア

    ターミナルで、接続先を指定してビルドします（例）:

    flutter build ipa --flavor stg -t lib/main_stg.dart

    成功すると build/ios/archive/ にアーカイブ、build/ios/ipa/ にアップロード用のファイルができます。stg / prod の指定を間違えないよう、コマンドをスクリプトにまとめておくと安全です。

  5. App Store Connect にアップロードする

    エンジニア

    次のどちらかの方法でアップロードします。

    • Xcode の Organizer: build/ios/archive/Runner.xcarchive を開く → Distribute App → App Store Connect → Upload
    • Transporter アプリ（Mac App Store で無料）: build/ios/ipa/ の .ipa ファイルをドラッグして「配信」

  6. 処理が終わるのを待つ

    エンジニア

    App Store Connect → アプリ → TestFlight に、アップロードしたビルドが「処理中」で表示されます。10〜30 分ほどで完了し、Apple からメールが届きます。

    「輸出コンプライアンス（暗号化）に関する情報がありません」と表示されたら、質問に回答します（通常の HTTPS 通信だけなら「免除」）。設定ファイル（Info.plist）で回答を固定しておくと、毎回聞かれなくなります。

  7. テスト内容を書いてテスターに配る

    プロダクトオーナー エンジニア

    ビルドの「テスト内容」に、今回の変更点や確認してほしいことを書きます（テスターの TestFlight アプリに表示されます）。テスターのグループに追加すると配信されます（10 章）。

C. Android: Google Play の内部テストへアップロードする

  1. アップロード鍵（keystore）を用意する（初回のみ）

    エンジニア

    エンジニアが keystore ファイルを作り、Flutter のプロジェクトから読み込むよう設定します（android/key.properties。この設定ファイルと keystore は Git に入れない）。keystore とパスワードはすぐにパスワード管理ツールに保存します。後で Codemagic に移行するときも同じ鍵を使います。

  2. バージョンを上げてビルドする

    エンジニア

    iOS と同じくビルド番号を増やしてから、ビルドします（例）:

    flutter build appbundle --flavor stg -t lib/main_stg.dart

    build/app/outputs/bundle/ に .aab ファイルができます。

  3. Play Console からアップロードする

    エンジニア

    Play Console → アプリ → テスト → 内部テスト → 新しいリリースを作成

    .aab ファイルをアップロードし、リリース名とリリースノート（変更点）を入力して「保存」→「確認」→「内部テストとして公開を開始」。初回は「Play アプリ署名」の利用を求められるので同意します。

  4. テスターに配る

    プロダクトオーナー

    内部テストのテスターには数分〜1 時間ほどで更新が届きます。テスターの招待は 10 章を参照してください。

Android のもう 1 つの選択肢: Firebase App Distribution を使うと、Google Play を通さずにテスト版（.apk）を配れます。Play Console の準備が終わる前でも配信でき、テスターは招待メールから専用アプリ経由でインストールします。ただし、アプリ内課金など Google Play が前提の機能は確認できません。

手動アップロードで気をつけること
  • テスト版は必ず stg 向けにビルドする。prod 向けを誤って配ると、テストのデータが本番に入ります
  • 証明書や keystore を特定のエンジニアの Mac にだけ置かない。必ずパスワード管理ツールに保管する
  • アップロードした人・ビルド番号・接続先・コードのバージョン（Git のコミット）を、チャットや管理表に毎回残す
  • Xcode と Flutter のバージョンをチームで揃える（Codemagic 移行時にも同じバージョンを指定する）
